# 上下文管理规则（Supplement）

> 可选增强模块。覆盖 Harness Engineering 两大支柱：**上下文架构**（支柱 1）+ **上下文隔离**（支柱 4）。
> 适用场景：多 Agent 协作、长对话上下文管理、大型项目信息治理。

---

## 核心原则

1. **上下文架构**：精准设计进入模型的信息——在正确的时机提供正确粒度的信息，避免信息过载。
2. **上下文隔离**：保持每个执行上下文的纯净性，防止跨任务、跨 Agent 的信息污染。

---

## 上下文架构（Harness Engineering 支柱 1）

### 信息优先级分层

Agent 读取项目文件时 MUST 遵循以下优先级：

| 优先级 | 信息类型 | 示例 | 何时读取 |
|:------:|---------|------|---------|
| P0 | 当前 Task 的 Spec + 直接相关源文件 | spec.md, 目标文件 | 每个 Task 开始时 |
| P1 | 架构约束 + 数据模型约束 | architecture.md, data-model.md | 每个 Phase 开始时 |
| P2 | 项目导航 + 命名约定 | AGENTS.md | 每次对话开始时 |
| P3 | 迭代记录 + 归档 | archive/ | 仅在排查问题时按需读取 |

### 延迟加载原则

- **MUST**: 不要在 Task 开始时一次性读取所有 `harness/` 和 `openspec/` 文件
- **MUST**: 先读取 `AGENTS.md` 导航，再按需读取具体文件
- **SHOULD**: 每个 Task 只读取 P0 + P1 优先级的文件，P2 已在对话初始化时加载

### 上下文健康指标（参考）

以下阈值因模型而异，作为参考而非硬性规则：
- 单次 Task 的上下文注入量 **SHOULD** 控制在模型上下文窗口的 **40%** 以内
- 超过阈值时 **SHOULD** 触发上下文压缩
- 对话中累计读取的文件数超过 **15 个**时，**SHOULD** 评估是否有冗余读取

## 上下文隔离（Harness Engineering 支柱 4）

### 任务级隔离

- **MUST**: 每个 Task 视为独立的执行单元，Agent 只需读取该 Task 相关的文件
- **MUST**: Task 之间通过文件系统传递信息（代码文件、测试文件），不依赖对话历史
- **MUST NOT**: 在 Task A 的上下文中假设 Agent 记得 Task B 的实现细节

### 信息接口化

当需要跨上下文传递信息时，MUST 通过以下结构化方式：

```markdown
## 上下文传递摘要

### 已完成的 Tasks
- T001: 类型定义完成，文件 `packages/shared/types/index.ts`
- T002: 常量定义完成，文件 `packages/shared/constants/index.ts`

### 当前 Task 需要知道的
- 可用的类型：[列出关键类型名]
- 可用的常量：[列出关键常量名]

### 当前 Task 不需要知道的
- 其他 Task 的实现细节
- 之前对话中的讨论过程
```

### 错误隔离

- **MUST**: Task 失败时，错误信息不传播到下游 Task
- **MUST**: 失败的 Task 标记为 `[!]`，附带错误摘要
- **MUST**: 下游 Task 开始前，检查依赖 Task 是否全部为 `[x]`

---

## 长会话管理

### 上下文压缩时机

当对话超过以下阈值时，SHOULD 进行上下文压缩：
- 对话轮次 > 20
- 已完成 Task > 5
- 累计修改文件 > 10

### 压缩方式

```markdown
## 上下文压缩摘要

### 项目状态
- 当前 Phase: N
- 已完成 Tasks: T001-T00N
- 当前 Task: TXXX

### 关键文件状态
[列出当前 Task 涉及的文件及其状态]

### 待解决问题
[如果有的话]
```

- **MUST**: 压缩后保留决策结论，丢弃推理过程
- **MUST**: 压缩后保留文件路径和状态，丢弃具体代码内容（Agent 可重新读取）
