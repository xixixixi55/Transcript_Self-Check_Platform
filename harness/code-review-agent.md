# 独立 Code Review Agent（Supplement）

> 实现 Harness Engineering「生成者与评估者分离」原则，解决同一 Agent 自审的乐观偏见问题。

---

## 核心原则

1. **上下文隔离**：Review Agent 拥有独立上下文，MUST NOT 共享开发 Agent 的对话历史
2. **严格评估偏向**：Review Agent 的系统提示偏向严格评估，而非乐观判断
3. **主动探测**：Review Agent SHOULD 主动读取代码、独立分析代码逻辑
4. **只审不改**：Review Agent 只输出审查结论和建议，MUST NOT 直接修改代码

---

## 触发时机

在 `/harness:apply` 的开发节奏中，每个 Task 的步骤 e（测试有效性验证通过）之后、步骤 f（标记 `[x]`）之前：

```
a. 写代码
b. 架构检查 + 类型检查
c. 写配套测试
d. 运行测试
e. 验证测试有效性
   ↓
e2. 【独立 Code Review】启动 Review Sub-Agent
   ├── 通过 → 继续
   └── 驳回 → 开发 Agent 修复 → 重新提交审查
   ↓
f. 标记 Task [x]
```

---

## Review Agent 系统提示

Review Sub-Agent 启动时 MUST 使用以下系统提示（独立于开发 Agent）：

```
你是一个严格的代码审查者。你的职责是审查代码变更的质量，而非实现功能。

核心原则：
- 你倾向于严格评估，宁可误报也不漏报
- 你不共享开发者的上下文，你需要独立理解代码
- 你只输出审查结论，不直接修改代码
- 你以项目的 Spec、架构约束和测试覆盖为评判标准
```

---

## Review Agent 审查清单

Review Agent MUST 按以下 5 个维度逐项审查：

### 维度一：架构合规性
- [ ] 文件放置在正确的架构层级目录
- [ ] import 依赖方向符合分层约束
- [ ] 未跳过中间层直接引用底层
- [ ] 横切关注点通过规定的策略处理

### 维度二：代码质量
- [ ] 文件行数不超过上限（250 行）
- [ ] 使用命名导出（除框架例外）
- [ ] 命名符合项目约定（参照 AGENTS.md 命名约定表）
- [ ] 无明显的逻辑错误或边界未处理
- [ ] 无硬编码的魔法数字或字符串
- [ ] 错误处理完整（异步操作有 try-catch / 错误边界）

### 维度三：Spec 一致性
- [ ] 代码实现与 Spec 场景（WHEN/THEN）一致
- [ ] 未引入 Spec 中 Non-Goals 明确排除的功能
- [ ] 与 design.md 中的技术决策一致

### 维度四：测试质量
- [ ] 测试覆盖了 Spec 中定义的场景
- [ ] 测试覆盖了边界条件和异常路径
- [ ] 测试断言具有区分度
- [ ] 测试命名清晰描述了被测行为

### 维度五：可维护性
- [ ] 代码职责单一
- [ ] 公共 API（导出的函数/组件）有必要的类型签名
- [ ] 与项目现有代码模式一致

---

## 驳回后的修复流程

1. 开发 Agent 阅读 Review Agent 的驳回报告
2. 按 MUST FIX 项逐一修复
3. SHOULD FIX 项默认修复，修复成本过高则记录到迭代记录
4. 修复后重新运行验证，重新提交 Code Review
5. **最多重复 2 轮**，第 3 次驳回 → 停止，请求人类介入
