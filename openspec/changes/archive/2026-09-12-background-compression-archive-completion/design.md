# Design: 后台压缩与归档完成统一导出

> 变更包：`background-compression-archive-completion`
> 分层约束遵循 `harness/architecture.md`：依赖单向（SharedTypes(0)→Constants(1)→Utils(2)；FE Hooks(10)→Components(11)→Pages(12)；BE Repo(20)→Services(21)→Controllers(22)→Routes(23)），前后端仅经 SharedTypes API 契约通信。

## D1. 案件打开「立即/稍后」后台压缩触发

**决策**：复用现有 workbench 后台归档任务机制（REQ-025 固定里程碑 + 资源准入 + 可恢复），把「案件打开选择立即/稍后」作为主触发；预览/审核页的手动 `EXECUTE_ARCHIVE` 同步路径降级为兼容入口，不再作为新交互主路径。

**理由**：REQ-012 已定义 `archive_deferred` 状态与「稍后压缩可恢复」场景，REQ-025 已有后台任务里程碑、资源准入、Worker 心跳与重启恢复——直接复用可避免重复建设，且满足「压缩不阻塞审核」。

**备选与拒绝**：
- 新建独立后台任务机制 → 与 REQ-025 重复，维护双套任务状态机，拒绝。
- 保持审核页同步 `EXECUTE_ARCHIVE` 为主 → 阻塞审核编辑且不满足「案件打开选择」，拒绝。

**实现要点**：
- 案件卡片/案件打开页在 `archive_deferred`/未压缩态提供「立即压缩」；点击后经现有 workbench 任务创建路径进入后台任务（attempt + 固定里程碑）。
- 任务推进中案件仍可编辑；任务与草稿编辑互不依赖（压缩只消费密封快照）。
- 归档发布证据继续绑定开始发布时的 attempt/binding/fence；发布短临界区内发生的审核保存不改写该证据。完成事务另以最新 shell/draft revision 与最新草稿指纹做 CAS，把 Manifest 派生字段合并到最新草稿，从而既保留证据边界，也不覆盖图片引用等审核编辑。
- 发布前允许 attempt/binding 随正式发布临界区之前的合法草稿保存推进，并使用校验时刻的最新草稿元数据；不得再把开始执行时的报告内容与当前审核草稿做稳定指纹相等校验。RAR 物理内容只由密封输入快照决定，审核字段和图片引用变化不构成归档中断条件。
- 若归档完成事务先于同一时刻的审核保存提交，草稿保存只对“当前 revision 恰为预期值 + 1、当前 lifecycle 为 `archive_verified`、且归档 verified intent 的更新时间与草稿更新时间一致”的完成回填做一次受限重试；重试时可信 RAR/MD5/附件1投影覆盖客户端旧副本，其余审核编辑（含图片引用）按客户端本次变更保存。其他 revision 冲突保持 409。
- 前端 hook 改为案件打开时查询案件状态并呈现选择，替换审核页手动 prepare 主路径。

## D2. 盘号后填：plan 阶段不再要求 first_disc_number

**决策**：`plan_archive` 允许 `first_disc_number=None` 执行（`expected_disc_numbers` 为空）；压缩完成后，由「盘号映射服务」按实际 part 数生成全序列并持久化映射。先填路径保持现行为（计划阶段生成预计序列）。

**理由**：需求明确「压缩前或压缩后输入首个盘号」；REQ-018 已允许盘号每槽独立、可修改、允许不连续，说明盘号本就是延迟决策的槽位属性，把强制前置条件放宽是自然演进。

**备选与拒绝**：
- 压缩后仍需重跑计划 → 浪费压缩结果，且可能触发重复压缩，拒绝。
- 维持压缩前必填 → 与需求相悖，拒绝。

**实现要点**：
- `archive_planner_service.plan_archive`：当 `first_disc_number is None` 时仅按体积计算 part（现有逻辑已按 volume 计算 `expected_part_count`），跳过 `parse_disc_sequence`/`generate_disc_numbers`。
- 新增 `disc_mapping_service`：输入首个盘号 + 实际 part 数 → `parse_disc_sequence` + `generate_disc_numbers` 生成全序列 → 按 part 顺序映射并持久化。
- Manifest 组装复用一次 `parse_disc_sequence` 的结构化结果：`sequence.date` 写入每个 part 的 `disc_date`，同一个 `sequence` 交给 `generate_disc_numbers` 生成连续编号；禁止根据前缀固定长度截取日期。
- 归档完成与已导出状态继续显示首盘号输入；输入初值优先取持久化 plan 的首个 active slot 映射。归档结果同时返回 plan 行 revision，提交时作为 CAS 令牌；再次提交复用同一映射服务，按当前实际 part 顺序整体替换映射，不修改或重跑 RAR，过期页面必须返回 revision conflict 而不是静默覆盖。
- 案件内单独 Word 导出携带 `case_id` 时，在盘号校验前读取当前案件最新 plan；全部 active slot 均具有 `confirmation=confirmed` 的非空映射时，以首个 slot 的盘号覆盖客户端草稿兼容字段。plan 映射是此场景的事实源：无 plan 时保留旧兼容行为；plan 存在但 pending、部分映射或空值时显式清空客户端盘号并由门控拒绝，不能用客户端兼容字段旁路。
- **复用指纹解耦**：REQ-012 的归档复用指纹含 `first_disc_number`（`archive_report_fingerprint`）。盘号后填/修改会导致指纹变化。需把盘号从复用指纹输入中剔除（或复用校验排除盘号），使后填不触发重复压缩。此为关键实现点，需在 apply 阶段用回归测试锁定「后填盘号复用已验证 RAR」。

## D3. 每 RAR 完成实时覆盖回填

**决策**：归档 attempt 完成时经 `complete_verified` → `update_verified_draft` 覆盖填写检查结果 `result`（rar_filename/md5_hash/file_size）并投影附件1。

**理由**：需求明确「每个最终 RAR 完成后同步填写检查结果与附件1」且已确认「实时填且覆盖手工值」。
**apply 阶段细化**：WinRAR 执行器批量产出分卷、不暴露逐卷完成事件，真实的「每 part 完成」点不可得；回填点取归档 attempt 完成（`complete_verified` 更新草稿，早于导出），在现有架构下是最早可执行时刻。独立 `attachment_backfill_service` 实现为重复死代码，Review 后删除。

**备选与拒绝**：
- 全部完成后一次性填（现状 usePreviewArchive）→ 回填在 attempt 完成时执行，早于导出且覆盖语义明确，拒绝「推迟到导出」。
- 仅填空白格、保留手工值 → 与用户确认的「覆盖手工值」相悖，拒绝。

**实现要点**：
- `complete_verified` 用 `verified_archive_result_fields` 从 manifest parts 派生 `rar_filename/md5_hash/file_size`（「、」分隔），经 `apply_verified_archive_result` 写入草稿 `inspection.result`，`attachment_projection` 投影附件1 `extract_list`。
- 审核字段尚未齐全而进入附件投影兜底路径时，“提取方式”仍按 Word 的硬件语义生成：`inspection.hardware_device` 为空时使用「取证设备」。前端对历史空值使用同一展示兜底，使既有草稿无需数据迁移即可看到该字段；显式已有值保持不变。
- 草稿更新受 revision CAS 保护，lifecycle 迁移到 `archive_verified`；回填只影响草稿投影，不影响已密封快照与 RAR 物理文件。

## D4. 保留 HashMyFiles 三列校验截图能力

**当前决策（T050，取代统一导出接线）**：`hashmyfiles_repository` 与 `hashmyfiles_service` 的真实窗口截图能力完整保留，但检查笔录统一导出不再调用该能力，也不发布 `hash-verification.png`。该模块作为后续鉴定文书流程的可复用能力保留；在鉴定文书合同落地前，不新增当前流程调用方。

**既有能力**：`hashmyfiles_repository`（Layer 20）用独立临时 `/cfg` 启动真实 HashMyFiles.exe 窗口；等待原生 ListView 出现全部结果后，通过 Windows 消息把可见列收敛为 Filename、所选摘要、File Size，再以 `PrintWindow` 捕获真实窗口为 PNG。临时配置、JSON、脚本全部清理。工具路径由 `BIJI_HASHMYFILES_PATH` 配置，未配置时回退到随包默认位置。

**理由**：用户进一步确认必须使用真实 HashMyFiles.exe 界面，而非仿制窗口。HashMyFiles 2.51 官方命令行提供 `/cfg` 与 `/files`，但不提供窗口截图或列筛选命令；因此使用隔离配置启动真实窗口，再在截图前临时调整其原生列表列宽，既保留真实彩色工具栏和 Windows 样式，也不污染用户日常配置。

**备选与拒绝**：
- 仿制 HashMyFiles 风格窗口 → 图标、标题栏和控件样式与真实 exe 不一致，用户验收不通过，拒绝。
- 继续发布 HTML → 与用户明确要求的截图产物不符，拒绝。

**保留能力的实现要点**：
- 关闭 Live Hashes，计算期间只低频探测完整摘要；单次原生窗口消息允许 5 秒响应，短暂无响应按 500ms 间隔重试并受动态校验总期限约束，摘要完整后才读取最终行。
- PNG 捕获真实窗口，列顺序固定为 Filename、MD5、File Size（HashMyFiles 原生标签，值为字节），多分卷逐行展示；截图前清除默认选中高亮。
- 结果完整后的窗口整理与截图使用独立宽限和有界重试；启动失败、校验总超时、窗口持续无响应、结果无效与真实截图失败通过无路径结构化结果分别映射，不再把所有非零退出统一包装为截图失败。
- 命令执行安全：仅允许配置的可执行路径，禁止用户注入参数；输出写入受控导出临时目录。
- 大体积超时：按待校验 RAR 总字节数以机械盘保守 5 MB/s 加固定启动余量动态估算，限制在 120 秒至 10 小时，并允许 `BIJI_HASHMYFILES_TIMEOUT_SECONDS` 在同一边界内覆盖。
- 部署：`BIJI_HASHMYFILES_PATH` 支持绝对路径或随包相对路径；hashmyfiles/ 目录按部署说明纳入（不纳入 Git 跟踪）。

## D5. 统一导出到用户路径

**决策**：统一导出流程为：案件绑定的 HTML 报告文件夹上一级目录作为固定输出位置 → 后端在该目录发布「最新编辑 Word + 全部 RAR」→ 记录导出日志并标记已导出。可重复导出时重新生成 Word，RAR 复用已验证分卷，不启动 HashMyFiles、不生成校验截图。

审核编辑界面的单独 Word 导出使用同一固定输出位置：用户确认 Word 文件名后，后端把最新 `.docx` 直接写入报告文件夹上一级目录，不打开导出目录选择器，也不读写目录历史。导出成功后页面保持在审核编辑界面。单独 Word 导出不复制 RAR、不生成 HashMyFiles PNG，也不把案件标记为统一导出完成。

**发布一致性**：Word 先在报告上级目录的同卷临时区完整生成，成功后才执行可回滚替换发布；新直出的 RAR 已在该目录中，统一导出只复核并复用，不再复制。只有历史工作区 RAR 首次迁移时才先复制并校验副本，成功后登记兼容位置并清理旧原件。成功发布同时移除同目录中由旧版统一导出留下的固定名 HashMyFiles PNG/HTML；任一步失败恢复上一版完整产物，不留下新旧文件混合包。

**目录边界**：统一导出发布阶段只访问案件报告来源推导并授权的上级目录；不得由客户端把 Word 或 RAR 重定向到其他位置。历史工作区迁移只处理 Manifest 明确列出的受控 RAR 原件。

**理由**：需求要求 Word 与 RAR 在报告上级目录形成可重复生成的完整产物集合；RAR 复用避免重复压缩，Word 用最新编辑保证审计内容为最终版本。

**备选与拒绝**：
- 保持单 Word 下载 → 不含 RAR，不满足统一导出需求，拒绝。
- 一次性导出并锁死 → 与「可重复导出」决策相悖，拒绝。
- 继续依赖浏览器下载设置、目录历史或 `showSaveFilePicker` → 会引入第二个输出位置事实源，并与报告来源决定目录的现行合同冲突，拒绝。

**实现要点**：
- 新增/改造导出端点：`POST /workbench/cases/{id}/export-bundle`；后端只接受与案件报告来源上一级目录相同的规范路径，并继续以一次性 `directory_token` 约束本次本机写入，不允许客户端重定向到任意目录。
- 路径安全：目录授权只绑定案件报告来源推导出的规范目录，`export_bundle` 消费校验，路径不一致或未授权时拒绝 `EXPORT_PATH_NOT_AUTHORIZED`。
- 单独 Word 路径导出继续复用 `/records/export` 的报告规范化、模板解析、盘号与附件门控及图片处理，只增加受控路径发布分支；请求携带由案件报告来源推导的 `export_path`、与该目录绑定的一次性 `directory_token` 及清洗后的 `word_filename`，成功响应返回最终文件名/目录而非 Blob。既有不带路径参数的 Legacy 兼容请求保留浏览器下载行为。
- 导出前重跑导出门控（REQ-009 全门控）；任一门控失败不标记已导出。
- 正式 Word 的图片事实源是最新草稿的 `asset_refs`，按该顺序解析并校验物理图片；禁止扫描案件资产目录兜底。历史草稿若仅缺 `photo_groups`，按检材顺序和每组两张图片生成确定性兼容映射；存在未绑定上传记录时明确返回图片尚未保存错误。
- 导出记录落库（路径、时间、part 集合），供「已导出」标记与审计；历史 PNG/HTML 字段继续作为旧记录兼容字段保留，但新记录不再写入。

**apply 阶段细化（用户实测反馈）**：
- 统一导出交互入口为**案件工作台卡片主按钮**，仅在底层 `archive_complete` 且满足导出条件时将其展示为「待导出」；该阶段在更多菜单保留「打开案件」与「删除案件」，其中「打开案件」返回审核编辑但不取代统一导出主操作。已导出阶段改以「删除案件」为推荐主操作，并在更多菜单保留「打开案件」「再次导出」。工作台经 `useArchiveCompletionStatuses` 自动加载归档结果，无需先点查看；案件打开页保留「立即/稍后」与补盘号入口，不再承载统一导出触发。
- 归档 inventory 性能优化：`verify_input_inventory` 改 `check_readability=False`（可读性由 seal 复制兜底）并移除第二轮重复 stat；`build_input_inventory` 文件 stat/open 用 `ThreadPoolExecutor` 并行（新增 `archive_input_inventory_worker.py`，复用 `BIJI_ARCHIVE_COPY_WORKERS`）。基准 3000 文件：verify 5.3s→0.87s、build 4.5s→1.7s。
- 原生目录选择器仅用于选择新的 HTML 报告来源；嵌入 C# 后台线程负责窗口归属、TopMost 与前台激活。选择器不读取或持久化报告、统一导出、单独 Word 的历史绝对路径；输出目录始终由当前案件报告来源推导。

## D6. 状态机与已导出/删除案件

**决策**：不新增持久化 lifecycle。继续使用既有解析、归档与 `exported` 事实；`archive_complete` 在工作台正向映射为「待导出」，待补盘号由既有归档结果与盘号映射事实派生。统一导出只在当前请求期间使用按钮 loading/禁止重复提交，刷新后以服务端 lifecycle 为准；「删除案件」复用 `case-workbench-delete`。

**理由**：复用现有事实避免双状态机；展示层只回答当前主状态和下一步操作，不改变业务流程与恢复语义。

**备选与拒绝**：
- 引入全新独立状态枚举 → 与 REQ-025/REQ-012 现有状态冲突，需全面迁移，拒绝。

**实现要点**：
- 「待补盘号」作为卡片展示态，由既有归档完成事实 + 盘号未映射派生，不新增持久化标志。
- 映射成功后审核页显式重读归档任务结果，用最新分卷映射重新派生「归档完成」并刷新分卷展示；不能只刷新不含结果明细的案件 shell。
- 导出路径提示只在盘号补齐后出现。
- 案件卡片以最终 lifecycle 为最高展示优先级：先对 `exported`、解析阶段、待处理、归档活动/失败、待补盘号和 `archive_complete` 作明确正向分支，再决定是否展示兼容的当前活动任务详情；历史任务不得覆盖最终状态。
- 每个阶段只显示一个实际可见的推荐操作：解析中无主操作，解析失败重试解析，待处理/归档中/待补盘号打开案件，待导出统一导出，已导出删除案件；低频能力收纳到更多菜单。待导出阶段的更多菜单必须保留「打开案件」，避免统一导出成为离开工作台后唯一可达路径。
- 已导出删除确认明确说明仅移除工作台案件与平台内受控产物，已导出到目标目录的文件不会被删除。

## D7. 大型分卷压缩的活动感知超时

**决策**：WinRAR 执行采用“低吞吐体积硬上限 + 输出无增长超时”。默认体积预算按 0.1 MB/s 计算，以覆盖部署电脑在多个磁盘密集型任务并行时实测约 0.3 MB/s 的单任务有效吞吐，并提供三倍耗时预算；硬上限增加固定收尾余量并限制在 30 天内。监控器持续统计 staging 中 RAR 文件总字节数，只有总大小严格增长才刷新空闲计时。默认无增长阈值由 10 分钟提高到 30 分钟，并允许通过受边界约束的配置覆盖；连续超过阈值没有任何输出增长时终止进程。

**理由**：机械盘上第一卷写满后，WinRAR 可能在处理下一批数据或执行卷收尾，RAR 文件会暂时不增长；前端此时已能显示已生成多个分卷，但压缩进程尚未完成。仅提高固定 timeout 会掩盖真正卡死，活动感知可以兼顾收尾时间和失控进程回收。

**实现要点**：
- `compute_timeout` 使用 0.1 MB/s 向上取整的体积时间并增加固定收尾余量，默认计算上限为 30 天；保留 `BIJI_ARCHIVE_TIMEOUT_SECONDS` 覆盖，但同步扩大并校验覆盖边界，非法值仍安全回退并写一条脱敏 warning。
- `monitor_owned_process` 以 RAR 输出总大小作为活动信号，支持可注入 probe 以锁定增长、缩小与停滞边界；首个非零 RAR 输出出现前不启用 idle timeout，仍受硬上限约束。hard 与 idle 均使用绝对 deadline，最早到期者优先，相等时 hard 优先；操作员环境变量覆盖逐字作为 hard deadline 使用。
- 无增长阈值默认 1800 秒，并通过独立、正整数且有上限的环境配置提供部署覆盖；它只治理输出停滞，不改变正常退出、完整性、所选哈希、Manifest 和发布门控。
- idle timeout 由 executor 映射为稳定的 `ARCHIVE_EXECUTION_TIMEOUT`，并先终止自有 WinRAR 进程、再清理 staging；若进程无法安全终止则返回 `ARCHIVE_EXECUTION_FAILED` 并保留 staging，禁止删除仍可能被进程使用的文件。分卷出现仅作为活动指标，不改变成功条件（正常退出、分卷校验、MD5、Manifest）。
- 完成事务从已验证 publish intent 的 Manifest parts 原子写入最终 `output_bytes` 与 `output_volume_count`，覆盖 WinRAR 退出前的周期采样，避免成功态保留少一卷的活动快照。

## D8. 机械盘基线下的完整性与统一导出超时

**决策**：磁盘密集型归档阶段统一以 0.1 MB/s 作为默认预算基线，覆盖多个磁盘密集型任务并行时实测约 0.3 MB/s 的单任务有效吞吐，并提供三倍耗时预算。`rar t` 完整性校验继续按实际全部 RAR 字节数动态计算内部超时；统一导出的前端请求上限按“RAR 完整复制一遍 + 固定编排余量”动态计算，不再包含 HashMyFiles 预算。内部与客户端最大上限统一提高到 30 天，避免旧 10 小时/24 小时上限先于体积预算到期。普通工作台请求、目录选择器、编辑租约和 SQLite 锁等待保持现有独立合同。

**理由**：统一导出仍需把全部 RAR 复制到用户目录的同卷 staging，外层请求必须覆盖大体积归档在机械盘上的一遍完整 I/O。截图退出当前调用链后继续叠加 HashMyFiles 最大预算会造成无意义的超长等待；归档自身的完整性校验预算保持不变。

**备选与拒绝**：
- 所有请求统一延长 → 会掩盖普通接口失联、锁竞争和会话失效，拒绝。
- 统一导出使用无限前端等待 → 无法回收真正失控的请求，拒绝；保留按已验证 RAR 总字节数计算的有界上限。
- 本轮把统一导出迁移为新的 durable 后台任务 → 会新增任务契约、持久化状态和恢复语义，超出本次机械盘超时回归的最小范围；若后续需要断点续作与刷新后恢复，另行演进。

**实现要点**：
- `compute_integrity_timeout` 使用 0.1 MB/s、固定余量和 30 天最大值计算 `rar t` 预算，继续以全部实际分卷总字节数为输入。
- HashMyFiles 保留能力同步使用 0.1 MB/s 和 30 天最大值；`BIJI_HASHMYFILES_TIMEOUT_SECONDS` 继续受同一边界约束，但不再影响检查笔录统一导出的请求预算。
- SharedUtils 根据归档结果 parts 的 `size_bytes` 汇总总字节数，按一遍机械盘复制加固定编排余量计算统一导出请求上限；大小缺失或非法时安全回退到既有最小上限。
- 前端两个统一导出入口都必须传入当前已验证 parts 的总字节数，不得继续无条件使用固定 30 分钟。

## 依赖与风险

## D10. 二进制档位与超大单卷模式

**决策**：容量名称继续使用 4GB、22GB、45GB，但字节值统一为 `GB = 1024³`。标准分卷最大卷数依次为 2、2、5，因此标准分卷阈值为 225GB。超过阈值的输入不再阻止，计划与 Manifest 写入 `archive_mode=oversized_single_volume`，`volume_size_bytes`/`volume_tier_gb` 为空；WinRAR 不传 `-v`，只允许 `<案件名>.rar` 单一产物。标准模式写入 `archive_mode=standard_split` 并继续执行逐卷容量校验。默认资源准入的输入上限提升到安全整数边界，不再在计划器之前以旧 135GB 默认值阻断；部署人员仍可通过 `BIJI_ARCHIVE_MAX_INPUT_BYTES` 显式设置本机安全上限。附件与 Word 计划保留超大单卷的空容量字段，不重新伪造光盘档位。

**理由**：超大单卷没有“每卷 45GB”上限，不能通过伪造更大档位或把输入大小写成分卷上限来绕过校验。显式模式使执行参数、物理产物、Manifest 和复核规则保持一致。

**兼容性**：历史 Manifest 没有 `archive_mode`，复核时继续按旧十进制容量解释；新生成 Manifest 必须带模式，避免存量归档因容量语义迁移立即失效。

**拒绝的方案**：不新增 75GB 档；也不把 225GB 作为系统总上限，因为需求要求超过阈值继续压缩为单卷。

## D9. 图片域 CAS 与本地草稿重基

**决策**：图片二进制仍由案件资产接口独立持久化；上传或恢复后的引用不再通过整份草稿 PATCH 绑定，而由图片字段级接口在最新草稿上合并。请求携带调用方最后观察到的有序图片 ID 作为图片域 CAS 基线，不携带可覆盖其他字段的旧报告快照。

**理由**：草稿 revision 同时承载审核保存、后台归档完成回填与附件投影。仅依赖全局 revision 会把无关字段推进误判为图片冲突；直接忽略 revision 又会覆盖另一会话真实的图片增删。图片域基线既允许无关 revision 收敛，也保留同域冲突保护。

**实现要点**：
- 后端每次尝试都读取最新草稿，先比较当前有序 `asset_refs` ID 与请求基线；相同才在最新报告上替换图片三字段，并复用既有草稿 Repository CAS、归档 binding 同步、资产注册校验和租约校验。
- Repository CAS 若被非图片写入抢占则有界重试；重读后图片基线变化立即返回 `PHOTO_BINDING_CONFLICT`，不做最后写入获胜式覆盖。
- `photo_groups` 由服务端按最新已保存 `evidence_list` 和有序图片 ID 确定性生成，客户端不能提交任意组映射。
- 成功响应返回完整最新草稿。前端保留本地未保存的非图片报告内容，但把 revision/生命周期/时间戳重基到响应草稿，并使 autosave 废弃旧请求、从新 revision 继续；图片操作的离页安全只取决于字段级绑定是否成功。
- 真实租约失效、资产引用不存在/不匹配和图片域基线冲突保持失败，不由重基逻辑吞掉。

## D10. 批量图片自然排序、原子接纳与单独 Word 容错

**决策**：在附件图片说明行新增独立的次要按钮「批量导入图片」，按钮打开支持多选的文件选择器；现有各检材图片槽位和逐张「添加图片」入口继续保留。批量选择先校验总数，再在客户端完成格式、大小和文件名排序。普通数字文件名继续按完整文件名自然排序，数字序号只决定相对顺序且不要求连续；整批均符合 `<检材顺序>-<图片顺序>` 时切换为位置分组规则，第一个数字表示当前检材列表的一基位置而非检材编号，第二个数字只允许 1 或 2，并要求每个检材位置恰有两个不同槽位。分组缺失、越界、重复或与普通命名混用时整批拒绝，避免自然排序碰巧可用却静默错配。只有总数恰好为当前检材数的两倍且其余条件全部通过时，才把排序后的完整列表一次性交给既有图片资产上传/绑定链路。任一批量前置条件不满足时不调用 `onChange`，因此不上传半批资产、不覆盖既有图片列表；数量不匹配即使同时混有坏文件，也优先返回包含当前检材数、应选数和实际数的完整计数提示。既有资产链路对上传和导出前读取统一使用最多 4 个并发任务，保持输入顺序，只在整批上传完成后执行一次草稿图片绑定，避免 200 多张图片产生无界请求洪峰；局部上传失败时记住已成功资产，重试只重传失败项。

**交互反馈**：按钮使用现有上传图标与默认次要按钮样式，避免与页面主导出操作竞争。说明文字保持「每个检材对应两张图片，按检材顺序依次对应」，并补充批量导入会按文件名数字排序。数量不匹配时使用完整、可操作的消息：「当前有 N 个检材，应选择 M 张图片；本次选择 A 张，未导入任何图片。」可访问名称与可见按钮文本均为「批量导入图片」。

**单独 Word 语义**：`/records/export` 的审核页单独 Word 分支把图片处理视为可选附件。发起导出时对已开始的图片上传/绑定只做最多 5 秒的有界等待；目录选择完成后重新读取最新已保存草稿，进一步缩小图片绑定推进 revision 的竞态窗口。若图片绑定仍在后续推进版本，后端仅在提交报告与当前报告除 `photo_ids`、`photo_groups` 外完全一致且图片字段确有变化时容忍该版本差异，非图片过期编辑继续返回 409。图片操作失败或超时不终止导出，而是以无附件2继续；图片完整且映射有效时照常生成附件2；零图片、图片缺失、数量不匹配、映射无效、未绑定、上传流读取或解码失败时，移除本次渲染使用的图片引用与分组并省略附件2，返回可展示但不阻断成功的图片提示。模板、目录授权、路径写入、报告数据和其他非图片门控保持原失败语义。统一导出继续使用其独立的正式产物完整性合同。

**分层实现**：Layer 2 在 `materialPhotoGroups.ts` 提供不依赖浏览器状态的文件名数字自然排序纯函数并覆盖跳号、不同位数和稳定同序边界；Layer 10 `useBatchImageImport.ts` 负责多选图片的原子校验和排序，`useCasePhotoAssets.ts` 对批量上传和导出读取实施保序有界并发，`useRecordExport.ts` 组装可选附件2请求并展示非阻断提示；Layer 11 `ImageUploader.tsx` 只在说明行接线独立按钮与多选文件入口，`reviewWorkspace.css` 负责说明和按钮的响应式排列；Layer 22 `record_controller.py` 负责最终移除图片门控及容错调用，防止客户端绕过或旧客户端仍使 Word 导出失败。

|------|------|
| HashMyFiles.exe 命令行/输出格式未知 | apply 阶段先一次性实测脚本固化，再实现 repository |
| 盘号后填破坏 Manifest 复用指纹 | D2 将盘号从复用指纹解耦，配回归测试 |

## D11. 归档模式决定光盘或硬盘介质语义

**决策**：不增加预压缩或二次压缩。继续由压缩前输入总量选择既有 `standard_split` 或 `oversized_single_volume`；前者固定投影为 `optical_disc`，后者固定投影为 `hard_drive`。恰好 `225 × 1024³` 字节仍属于标准光盘分卷。压缩后的 `actual_archive_bytes` 继续只作为产物事实，不反向改变模式。

**理由**：现有模式已经稳定决定 WinRAR 是否携带 `-v` 和最终是多卷还是一个完整 RAR。直接复用该事实源能保持一次压缩、Manifest 复核与历史产物兼容，同时修复超大单卷仍被文书误称为光盘的问题。

**编号与兼容性**：审核编辑界面以单个完整字符串作为编号唯一输入入口。标准分卷同时接受 `GPyyyyMMdd-序号` 与 `GPyyyyMMddXX-序号`，并按实际 part 顺序生成连续编号；超大单卷同时接受一个 `YPyyyyMMdd-序号` 或 `YPyyyyMMddXX-序号`，不得生成后续编号；可选的 `XX` 为两位数字用户标识，生成后续编号时保持不变。新旧格式在提前规划、后填映射、修改、展示和导出路径中行为一致，系统不得自动补写或删除用户标识。持久化与既有 HTTP 路径暂保留 `disc_number`/`disc-mapping` 等历史字段名，公共结果同时投影明确的 `archive_mode`/`archive_medium`，避免本次引入数据库迁移并保持存量调用兼容。错误介质前缀不得成为完成映射。

**Word 投影**：`AttachmentPlan` 携带介质类型。光盘摘要列出全部实际编号；硬盘固定一页、一块，检查结果使用“拷贝的方式保存在”，附件摘要使用“本鉴定中心拷贝的”，附件3把编号标签、时间标签和末尾说明切换为硬盘语义。

**拒绝的方案**：不按压缩后实际大小重新规划，因为那会要求先生成完整 RAR 后对光盘案件二次压缩；不把多个 RAR 分卷共同映射为一块硬盘，因为超过阈值的现有正式合同要求一个完整 RAR。

## D12. 报告上级目录直出与旧归档位置兼容

**最终决策**：案件持久化的 HTML 报告来源唯一决定 RAR 与 Word 的最终目录。新归档直接在报告上级目录的任务独占临时目录中生成、校验并以同卷排他重命名发布，不再提供独立 RAR 工作与存储根设置，也不在应用工作区生成第二份正式 RAR。

**用户数据边界**：`%LOCALAPPDATA%\文枢` 继续保存 SQLite、案件资产、模板、日志和单实例锁。归档 publish intent 在 SQLite 中持久化新直出的绝对内部定位符；当前工作台结果、恢复和统一导出优先使用该权威。没有生产写入者的上传与备份目录不在首次启动时预创建，由未来实际消费者按需建立。

**兼容边界**：旧 `archive-storage-settings.json` 只读解析历史工作区位置，旧 `archive-export-locations.json` 只用于缺少 SQLite 绝对发布定位符的历史结果或历史工作区迁移。新直出不再向旧 JSON 位置表重复登记。兼容读取保持有界且不得使新任务回退到系统盘工作区；待历史迁移合同正式退役后再删除兼容 Repository 和旧文件。

## D13. 失败收敛后的受控重试重基

**决策**：重试仍以调用方提交的 task revision 和 case revision 作为并发基线。唯一例外是当前任务已经收敛为 `failed_retryable`/`interrupted`，且失败处理只把案件壳与草稿生命周期推进为 `archive_interrupted`、案件 revision 恰好增加一版时，服务端可把重试基线重基到当前 revision。新任务与 attempt 仍由既有事务化准备链路创建，不能绕过其 CAS。

**安全边界**：受控重基必须同时确认当前失败任务仍是该案件最新任务、失败 attempt 绑定该 task、来源 ID/revision 与可用状态未变化、草稿 revision 与 attempt 捕获值一致、报告指纹一致且案件壳和草稿均处于 `archive_interrupted`。任一条件不满足都保留 `REVISION_CONFLICT` 或 `ARCHIVE_TASK_STALE`；因此真实用户编辑、来源重检、新任务或多版推进不会被内部状态收敛伪装。

**竞态处理**：上述读取只用于识别可重基候选。识别后若又发生并发写入，enqueue 的归档准备事务会再次校验 shell/source/draft revision 并拒绝，不依赖先检查后使用窗口保证安全。
