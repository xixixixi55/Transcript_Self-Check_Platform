# 验证节奏与运行环境

> 本文承载候选冻结、人工验收、完整门控环境预检和日志输出细则。级别判断与必跑门控仍以根目录 `AGENTS.md` 为准。

## 1. 候选冻结

候选冻结表示需求理解、实现和适用的人工验收均已收敛，准备进入最终审查与完整门控。冻结不是 Git 操作，也不要求创建额外分支或提交。

满足下列条件后才能冻结候选：

- 变更包中的实现任务已完成，自动化定向测试覆盖受影响行为；
- UI 视觉、真实 Word/PDF、桌面工具或真实业务流程等无法由自动化可靠覆盖的内容已经人工验收；
- 不适用人工验收时明确记录 `manual_acceptance: N/A`，不得留下含糊的“待确认”；
- 已知反馈已处理，没有仍会改变源码、接口、数据模型、测试预期或正式行为的开放项。

冻结前只运行受影响的定向测试和级别要求的轻量检查。适用人工验收时，应先生成可验收产物并获取反馈，再运行最终 Review 和完整门控，避免对必然还会变化的候选重复执行高成本验证。

## 2. 反馈补丁

人工反馈不单独创建同目标变更包。反馈仍属于当前需求时，在原变更包追加任务、实现和证据：

1. 修改受影响实现并运行失败用例或最小定向测试；
2. 行为或验收标准变化时同步修改当前 delta spec；
3. 重新完成受影响的人工验收；
4. 开放项清零后冻结候选。

候选冻结后若源码、接口、数据模型、测试预期或正式行为发生变化，候选自动解冻。Review 是否失效按 `harness/code-review-agent.md` 判断；完整门控必须基于重新冻结后的候选执行。

### Word/DOCX 版式断言范围

DOCX 自动化回归应只比较需求实际约束的 OOXML 属性和结构，例如分页、缩进、行距、对齐、VML 图形或锚点关系；除非需求明确要求节点完全同构，不得对整段 `w:pPr` 或整块 XML 做字节级相等断言。运行时占位符替换和合法规范化可能改写与目标版式无关的默认运行属性。真实分页与视觉位置仍须使用 Microsoft Word/PDF 人工验收覆盖，XML 断言不能替代排版引擎验证。

## 3. 完整门控预检

`verify:full` 在工程检查前执行环境预检，默认读取 `harness.config.yaml` 的 `verification.preflight`：

- 临时目录存在且可实际写入；
- 临时目录路径长度不超过配置上限；
- 临时目录所在卷的可用空间不低于配置下限。

Windows 默认使用项目所在卷根目录下的短路径 `harness-temp-root`；例如项目位于 D 盘时使用 `D:\harness-temp-root`。目录不存在时由预检创建。非 Windows 环境默认使用系统临时目录；需要显式覆盖时设置 `HARNESS_TEMP_ROOT`。完整门控会将子进程的 `TEMP`、`TMP` 与 npm cache 指向该目录，避免包管理器继续耗用原系统盘。

预检失败属于环境阻断，不计作实现验证失败，也不触发盲目重跑。先按输出修复环境，再重新执行门控。任务特有的外部工具、GUI 进程或数据库前置条件仍由受影响模块的定向验证负责，不放进全局默认预检。

## 4. 输出与失败诊断

完整门控逐阶段运行。阶段通过时只输出阶段名、`PASS` 和耗时；阶段失败时停止后续阶段，输出 `FAIL`、有限的日志尾部和完整日志路径。

完整日志写入预检后的临时根目录。全部阶段通过时自动清理本次日志目录；失败日志保留用于下钻。不得把完整通过日志重新复制到任务上下文或报告中。

失败后先判断类别：

- 明确的实现回归：修复后先跑失败用例，再跑受影响模块；
- 明确的环境问题：修复环境后重跑原门控；
- 疑似偶发测试：只允许隔离复跑失败用例用于诊断，并记录两次结果。

隔离复跑通过不能替代最终门控，也不能把未登记的失败自动标记为通过。候选完成修复并重新冻结后，最终门控仍须完整通过。
