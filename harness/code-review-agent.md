# 独立 Code Review Agent（Supplement）

> 实现 Harness Engineering「生成者与评估者分离」原则，解决同一 Agent 自审的乐观偏见问题。
>
> **适用范围**：独立 Code Review Agent 默认用于 **Level 3**，或涉及公共接口、核心数据模型、安全边界和高风险跨模块行为的 Level 2 任务。
> **Level 1 不要求启动独立审查 Agent。**
> 默认关闭，按需启用（`harness.config.yaml` 中 `code_review_agent: false`）。

---

## 核心原则

1. **上下文隔离**：Review Agent 拥有独立上下文，MUST NOT 共享开发 Agent 的对话历史
2. **严格评估偏向**：Review Agent 的系统提示偏向严格评估，而非乐观判断
3. **主动探测**：Review Agent SHOULD 主动读取代码、独立分析代码逻辑
4. **只审不改**：Review Agent 只输出审查结论和建议，MUST NOT 直接修改代码

---

## 触发时机与审查范围

- **Level 1**：不要求启动。
- **Level 2**：按需启用；只有审查能发现明显的公共影响、核心数据或安全问题时才使用。
- **Level 3**：按 `harness/verification-strategy.md` 冻结候选后统一审查一次，不按 Task 启动。审查证据可以是独立 Review Agent 报告，也可以是人工审查记录。

审查完成后再执行最终自动化门控。开发过程中的定向测试可以提前运行，但不能因此增加一轮重复的最终模块门控。

---

## Review Agent 系统提示

Review Sub-Agent 启动时 MUST 使用以下系统提示（独立于开发 Agent）：

```
你是一个严格的代码审查者。你的职责是审查代码变更的质量，而非实现功能。

核心原则：
- 你倾向于严格评估，宁可误报也不漏报
- 你不共享开发者的上下文，你需要独立理解代码
- 你只输出审查结论，不直接修改代码
- 你以项目的 Spec、架构约束和测试覆盖为评判标准
```

---

## Review Agent 审查清单

Review Agent MUST 按以下 5 个维度逐项审查：

### 维度一：架构合规性
- [ ] 文件放置在正确的架构层级目录
- [ ] import 依赖方向符合分层约束
- [ ] 分层编号仅用于依赖方向，未为补齐 Repo→Service→Controller→Route 形式层级创建无职责中间层
- [ ] 横切关注点通过规定的策略处理

### 维度二：代码质量
- [ ] ≤400 行作为推荐目标；400–600 行的高内聚模块未仅因 LOC 被要求拆分
- [ ] 600–800 行已评估自然职责边界并登记说明；>800 行已拆分或登记明确、有界的豁免理由
- [ ] 模块拆分由领域职责、变化原因或可独立测试的行为边界驱动
- [ ] 新增 Service/Repository 具有可独立描述的领域职责，不是仅承担行数拆分的 support/helper/pass-through
- [ ] 使用命名导出（除框架例外）
- [ ] 命名符合项目约定（参照 AGENTS.md 命名约定表）
- [ ] 无明显的逻辑错误或边界未处理
- [ ] 无硬编码的魔法数字或字符串
- [ ] 错误处理完整（异步操作有 try-catch / 错误边界）

### 维度三：Spec 一致性
- [ ] 代码实现与 Spec 场景（WHEN/THEN）一致
- [ ] 未引入 Spec 中 Non-Goals 明确排除的功能
- [ ] 与 design.md 中的技术决策一致

### 维度四：测试质量
- [ ] 验证证据覆盖了本次修改的关键风险和相关 Spec 合同
- [ ] 高风险逻辑覆盖了必要边界和异常路径，低风险修改未机械堆叠重复测试
- [ ] 测试断言具有区分度
- [ ] 测试命名清晰描述了被测行为

### 维度五：可维护性
- [ ] 代码职责单一
- [ ] 公共 API（导出的函数/组件）有必要的类型签名
- [ ] 与项目现有代码模式一致

---

## 驳回与复审流程

1. 开发 Agent 阅读 Review 报告并按 MUST FIX 项修复。
2. 修复后运行受影响的定向测试。
3. 修改被审查的核心逻辑、接口、数据模型、正式行为或测试预期时，相关结论失效并按受影响范围复审。纯文案、样式、格式、命名或注释只需受影响 diff 检查，除非其本身属于正式合同；修改测试断言、fixture、mock、覆盖范围或预期结果时必须复审。
4. 反馈修复阶段先运行受影响定向验证，不立即重复最终 Review/full gate；开放项再次清零并重新冻结后统一复审，再运行一次 `verify:full -- --change <name>`。全局发布/集中归档使用 `verify:full:all`。最终验证失败导致实现修改时，仍按上述规则处理。
5. 连续两轮修复仍未通过时停止并请求人类介入；不按每个 Task 单独启动审查。
